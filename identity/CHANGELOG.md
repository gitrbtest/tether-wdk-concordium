# Changelog

User-facing changes to `@concordium/wdk-identity-concordium` are recorded here.

## [Unreleased]

### Added

- Package scaffold: entry point, type declarations, unit-test setup and CI validation.
- Configuration presets `CONCORDIUM_MAINNET_IDENTITY_CONFIG` and `CONCORDIUM_TESTNET_IDENTITY_CONFIG` (`useMainnetKeyDerivation`, `walletProxyUrl`).
- `IdentityProviders`: list the identity providers a wallet-proxy publishes, and get one by its index, with issuance and recovery addresses exactly as published. `IdentityProviderError` for unpublished providers.
- `ConcordiumIdentity`: start identity verification with `createIdentityRequest`, which builds the identity request from the wallet seed and returns the link to the provider's verification page. `dispose()` zeroes the seed.
- `ConcordiumIdentity`: collect the issued identity with `retrieveIdentity`, which reads the provider's reply from the callback address and polls until the identity is issued or refused; after `createIdentityRequest` on the same object, the callback address is all it needs. `parseIdentityCallback` and `waitForIdentity` do the same in two steps, to resume after an app restart. The identity is checked to belong to the wallet's seed and kept inside the object; only a summary is returned, and `dispose()` zeroes it too.
- `IdentityIssuanceError`, with `reason` `'provider-error'`, `'rejected'`, `'timeout'` or `'cancelled'`, and the provider's `detail` (and `code`, if given).
- Optional built-in callback listener for Node.js desktop and server wallets, from the separate entry point for Node.js extras `@concordium/wdk-identity-concordium/node`: `listenForIdentityCallback` receives the provider's return on 127.0.0.1 at a random secret path, with a timeout and cancellation.
- Example `examples/verify-identity.mjs` (`npm run example:verify-identity`): identity verification end to end on testnet, saving the identity encrypted; `OPEN_BROWSER=1` opens the verification page.
- Encrypted identity storage: `ConcordiumIdentity` takes a `store` and gains `saveIdentity`, `loadIdentity` (no network call) and `deleteIdentity`. The store only receives encrypted bytes and slot names; the key is derived from the seed (HKDF-SHA256), never stored, and wiped after use; AES-256-GCM, bound to the slot. Saving never silently replaces a different saved identity (`{ replace: true }` to do so). Format documented in `docs/storage-format.md`.
- `IdentityStorageError`, with `reason` `'unreadable-slot'` or `'slot-in-use'`.
- Stores: `MemoryIdentityStore` (main entry); `FileIdentityStore` (from `/node`): one file per slot, safe writes, owner-only permissions where supported. Any object with `save`, `read` and `delete` works as a store (`IdentityStore` type).
- `verifyIdentityStore`, from the testing entry point `@concordium/wdk-identity-concordium/testing`: checks a store against the contract, in any test framework.
- Examples `load-identity` (load a saved identity in a new program) and `database-store` (a store on SQLite, built into Node.js 22.13+).
- Account creation: `ConcordiumIdentity.createAccount` creates an account on chain from the identity held (collected, or loaded from the store), with no ID App, and returns once it is final. Several accounts per identity through `credNumber`; attributes are revealed only when named in `revealAttributes`; an account that already exists is returned with `created: false` and nothing is sent. The result's `path` (`provider/identity/credNumber`) is what `@concordium/wdk-wallet-concordium`'s `getAccountByPath` takes. Sent through the wallet-proxy; no node connection needed.
- `AccountCreationError`, with `reason` `'identity-expired'`, `'max-accounts'` or `'unknown-attribute'` (found before anything is sent), or `'rejected'`, `'expired'`, `'timeout'`, `'cancelled'` or `'wallet-proxy'`, with the account's `address`, the `transactionHash` and a `detail` when known.
- Live test, run only with `WRITE=1`: creates a real testnet account (account numbers 100–199 of the recorded test identity are reserved for it) and checks it exists on chain.
- Example `create-account` (`npm run example:create-account`): create an account on testnet from a saved identity, and see it on CCDScan.
- Example `wdk-end-to-end` (`npm run example:wdk-end-to-end`): an account created from the saved identity, used through `@concordium/wdk-wallet-concordium`: receives CCD, a PLT and a CIS-2 token, sends some back with the fee quoted first, and a second account with no CCD sends a PLT with its fee paid by a sponsor. The wallet package is a development-only dependency, for this example.
- Dependency `@concordium/rust-bindings`, pinned to the exact version `@concordium/web-sdk` uses (a test keeps them in step), for the signed credential in the form the wallet-proxy takes.
- Recovery from the seed alone, e.g. on a new device: `ConcordiumIdentity.recoverIdentity` asks the provider's published recovery address for one identity (by provider and identity number), checks it belongs to the seed and holds it, as after verifying; `null` if the provider has none. `findAccounts` lists an identity's accounts on chain (account 0, 1, 2 … from the seed, until `gap` missing in a row, default 3), each with the `path` for `getAccountByPath`. `recoverAll` does both for every provider with a recovery address and identity 0, 1, 2 … (`identityGap`, `accountGap`), returning `{ identities, problems }` so one provider failing does not lose the others. Read-only: no transactions, no fees.
- `IdentityRecoveryError`, with `reason` `'provider-error'`, `'not-yours'`, `'network'`, `'wallet-proxy'` or `'cancelled'`, and the provider's `status` and `detail` when given.
- Example `recover-identity` (`npm run example:recover-identity`): recovery on a new device on testnet with `recoverAll` alone, then the accounts' balances through the wallet package. Read-only.
- Live test (read-only, run with the other live tests): the recorded test identity comes back from the testnet provider, with its account 0; an identity never issued comes back as `null`.
- "What you can build" in the README: short stories of what the package makes possible, each with a demo to run.
- Proving facts to websites (account-based, in Concordium's own request format, as WalletConnect's `request_verifiable_presentation` carries it): `describeProofRequest` reads and checks a website's question and describes it in plain English for the consent screen (no network, no secrets); `ConcordiumIdentity.prove` answers it with a proof from one of the identity's accounts, revealing only what the question asks to see; `accountsThatCanAnswer` lists the identity's accounts that can truly answer. The wallet refuses before building anything if the identity has expired, its provider is not accepted, or its details do not satisfy the question, so it never makes a false answer. The question is accepted as `{ challenge, credentialStatements }` or WalletConnect's `{ paramsJson }`.
- `ProofError`, with `reason` `'invalid-request'`, `'unknown-attribute'`, `'not-held'`, `'identity-expired'`, `'provider-not-accepted'`, `'cannot-prove'` or `'node'`, and a `detail` when known.
- The website's side of proofs, from the separate entry point `@concordium/wdk-identity-concordium/verify` (servers, Node.js): `requestFor` builds a question (`adult`, `minAge`, `residentIn`, `notResidentIn`, `nationalityIn`, `nationalityNotIn`, `documentValid`, `reveal`) with a fresh random challenge; `connectToNode` connects to Concordium's public node or your own; `checkPresentation` checks an answer: the same challenge and statements, an accepted provider, the right network, the account on chain, its identity still valid (an expired identity's proof still adds up, so this matters), and the proof itself with Concordium's verifier. A refused answer returns `{ ok: false, reasons }` with plain messages; it throws only if the node cannot be asked. Challenges are compared ignoring letter case and "one of / none of" lists ignoring order, as Concordium's proofs write them back. No new dependency.
- Example `age-check` (`npm run example:age-check`): both sides of an age check on testnet: a shop asks "over 18?", a wallet with only the seed phrase recovers its identities and answers with an account that can, the shop checks the answer against the chain and refuses the same answer sent again. Read-only.
- Proof tests: offline, with the recorded identity and its account's sealed details as recorded from the chain (answers checked with Concordium's verifier and with `checkPresentation`; challenge, statements, provider, network, expired and not-yet-valid identities, tampered proofs); compatibility with Concordium's published example apps, answering their exact questions; and live, read-only tests checking answers against testnet.
- "Proving facts" in the README, with what a website must do itself (one answer per question, keep the outcome, fresh challenges, dates worked out on the day, refuse identities that are not valid).

### Changed

- **The identity provider list is passed in; the package does not fetch it**: new required configuration field `identityProviders`, the list in the shape of the wallet-proxy's `/v1/ip_info`, so any source giving that shape works if the wallet-proxy is replaced. It is checked when the object is created, with errors naming the wrong field. `new IdentityProviders(list)` takes the list (it used to take the configuration and fetch it). The presets no longer make a complete configuration on their own: `{ ...CONCORDIUM_TESTNET_IDENTITY_CONFIG, identityProviders }`. The samples, the demo wallet and the provider check fetch the list once and pass it in; the live tests use the live list.
- **The package stores nothing; the wallet keeps the identity its own way**: new `exportIdentity` gives the identity as text, **encrypted by default** (key from the seed, never stored; reveals nothing personal; which identity it is stays readable; any change detected) or plain JSON with `encrypted: false`; new `importIdentity` takes either form back after checking it is this wallet's (an encrypted export by decrypting it, with no network call; a plain one by its public key). Removed: the `store` option, `saveIdentity`, `loadIdentity`, `deleteIdentity`, `MemoryIdentityStore`, `FileIdentityStore` (from `/node`), `verifyIdentityStore` and the `/testing` entry point, the database-store example. `IdentityStorageError` reasons are now `'unreadable'` and `'not-yours'`. The encrypted export is format version 2 (the label travels in the text); version-1 data saved by the store-based versions is still read, given its numbers. `docs/storage-format.md` describes both, with golden test vectors. The samples keep exported identities in a folder (`IDENTITY_FOLDER`, was `IDENTITY_STORE`).
- **No default identity or account number**: `identityIndex` is required by `createIdentityRequest`, `recoverIdentity`, `findAccounts`, `prove` and `accountsThatCanAnswer` (and by `waitForIdentity` together with `providerIndex`), and `credNumber` by `createAccount` and `prove`. They used to default to 0, which could quietly use the wrong identity or account (for example, `createAccount` returning an existing account 0 instead of creating a new one). A missing number is an error that says how to find it. New helpers: `nextIdentityIndex` (the number for a new identity with a provider) and `nextCredNumber` (the number for a new account under an identity). The verify-identity and create-account examples use them when no number is given.
- The main entry no longer uses Node.js-only features, so it is meant to run outside Node.js too; a test keeps it that way.
- The network's cryptographic parameters are read once per `ConcordiumIdentity` instead of for every request.
- Every example now explains each step in plain English in its code comments.
- Clearer wording in the docs and code comments: loading an identity reads only the store (no provider, wallet-proxy or chain call; the store itself may be remote), and deleting what is not saved does nothing.
